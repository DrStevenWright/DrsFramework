# DrsXrPlatform

Five modules with different load rules. Startup order matters: `DrsXrArbiter` starts at `EarliestPossible` and selects the desktop OpenXR runtime, OpenXR creates its instance at `PostConfigInit`, and the arbiter picks the vendor plugin type once config is ready.

| Module | Type, phase | Platforms | Role |
|---|---|---|---|
| `DrsXrArbiter` | Runtime, EarliestPossible | Win64, Android | XR arbiter: desktop OpenXR runtime and vendor plugin selection; early XR state shared by the others |
| `DrsXrPlatform` | Runtime, PostConfigInit | Win64, Android | Device state, OpenXR hand extensions, hand tracking settings and the `UDrsXrPlatformLibrary` API |
| `DrsXrMixedReality` | Runtime, PostConfigInit | Win64, Android (passthrough on Android only) | `UDrsXrPassthroughSubsystem` |
| `DrsXrPlatformEditor` | Editor | | Per-user editor setting for the vendor plugin type |
| `DrsXrPlatformTests` | DeveloperTool | | `Drs.XrPlatform.*` tests |

**No vendor plugin is needed.** No Drs module links one or lists one in the `.uplugin`: the framework calls the OpenXR extensions it needs directly, whoever provides them, so it works the same with a vendor plugin running or absent. Vendor plugins live in host projects. DrsTestProject has the private MetaXR fork as a submodule at `Plugins/MetaXR` (branch `drs`), integrated with the arbiter, so it loads only when the arbiter picks Meta; projects keep it for Meta-only features (anchors, scene, MRUK). The fork never loads OVRPlugin (a `DRS:` patch in `FOculusXRHMDModule::PreInit`), since it runs on Epic's OpenXR only (`XrApi=NativeOpenXR`). There is no Pico vendor plugin yet, but the Pico vendor entry and the Pico runtimes stay in config, so one can be added without code changes.

- **Running alongside a vendor plugin.** The native code checks `GetXrPluginType()` and skips only what a vendor plugin may also do with side effects: the hand interaction bindings (a second `xrSuggestInteractionProfileBindings` call for the same profile replaces the first, and MetaXR suggests microgestures there). Extension requests and reads (GPU utilisation, hand aim) always run, since duplicates are harmless. Simultaneous hands and controllers is still resumed, because MetaXR pauses it at session start and nothing else resumes it.
- **Check the extension, not the plugin.** Over SteamVR a Meta headset still makes the arbiter pick Meta, but no Meta extension is offered. Code that needs an extension checks `IsExtensionEnabled` and the system properties.

## DrsXrArbiter: the XR arbiter

Makes two independent choices: the desktop OpenXR runtime (at startup, see the next section) and which vendor XR plugin's modules load, so that competing vendor plugins (Meta, Pico) can be enabled together. Plugin arbitration is optional: a vendor plugin that isn't integrated loads as normal. The MetaXR fork is integrated. The integration steps for vendors are in the comment at the top of `Public/DrsXrArbiter/DrsXrArbiter.h`.

- **Vendors are names, not an enum.** A vendor's ID (`Meta`, `Pico`) is its `Id` in the vendor table, and is what `.uplugin` files, overrides, `GetXrPluginType()` and `FXrSelection` use. Adding a vendor needs config only.
- **Opting in:** in a `.uplugin`, set a module's `LoadingPhase` to `None`, put its real phase in `ArbitratedLoadingPhase`, and name its vendor in `ArbitratedXrPlugin`, on the module or at the plugin's top level. The arbiter reads the raw descriptor JSON because the engine drops unknown keys. `EarliestPossible` can't be arbitrated. Several plugins can name the same vendor (say PicoOpenXR and PicoEnterprise for Pico): the arbiter starts all of their modules together, or none. The vendor still has one vendor-table entry and one marker module.
- **Vendor shaders need an unarbitrated mapping.** A vendor module's global shaders register as soon as its DLL loads, which happens whenever another module links it, even if the arbiter never starts it. Without the shader directory mapping the editor then fails fatally at startup. So an integrated vendor plugin needs an unarbitrated module that maps its shader directory at `PostConfigInit`, and its own mapping must skip if the directory is already mapped. The MetaXR fork has `OculusXRShaders` for this.
- **Choosing the vendor** (`Private/DrsXrArbiter.cpp`), once config is ready at `PostConfigInit`. The vendor table's keywords are matched, ignoring case, and the first vendor with a match wins.
  - Android: the project override, then the device's brand (`ro.product.brand`) and manufacturer. Quest reports `oculus` and `Oculus`.
  - Editor: the editor setting (`UDrsXrPlatformEditorSettings`, restart required), the project override, the selected runtime's `Vendor`, then the device name.
  - Desktop game: `-noHMD` selects none; then `-XrPlugin=<Id>`, the project override, the selected runtime's `Vendor`, and finally the HMD device name once the HMD module is up (too late for that vendor's OpenXR extensions, which only matters over SteamVR, whose system name is `SteamVR/OpenXR : oculus` for a Quest).
  - Commandlets load every vendor, so everything cooks. Dedicated servers load none.
- Phases that pass before the vendor is known are queued and loaded as soon as it is.
- **Config:** `Config/DefaultDrsXrPlatform.ini` holds the runtime table (`Runtimes`, `RuntimePriority`) and the vendor table (`Vendors`: `Id`, `Keywords`, `MarkerModule`), both under `[/Script/DrsXrArbiter.DrsXrArbiterSettings]`. `UDrsXrArbiterSettings` (Project Settings > DRS > XR Arbiter) shows them in two categories, OpenXR Runtime and Vendor Plugin, with the project override. It is the plugin's own config file (the settings class has `Config = DrsXrPlatform`), so a project's `Config/DefaultDrsXrPlatform.ini` overrides it, and Project Settings writes there; `!Runtimes=ClearArray` and the like replace a table. Don't move the tables back to a plugin `Config/Game.ini`: the engine applies that over the project's `DefaultGame.ini`, so a project could add entries but not remove, reorder or edit them. Both tables are read through `GConfig` at `EarliestPossible` (plugin config is mounted before any plugin module loads), before reflection can import text, so `FConfigText` (`Public/DrsXrArbiter/DrsXrConfigText.h`) parses the struct text. It reads what Project Settings writes, and the `EditorExport` test checks that. The settings classes only make the tables editable. The vendor table is read once and cached, since `GetXrPluginType()` runs often. Both overrides list the vendor IDs through `UDrsXrArbiterSettings::GetXrPluginOptions` (`GetOptions`); the editor setting names it in full, `DrsXrArbiter.DrsXrArbiterSettings.GetXrPluginOptions`, rather than wrapping it.
- **`GetXrPluginType()` detects the running vendor** from its marker module in the vendor table (`OculusXRHMD`, `PICOOpenXRHMD`), so it is right whether the arbiter or the engine loaded the plugin, and None without one. `GetArbitratedXrPluginType()` is the arbiter's own choice. `FXrSelection` (`Public/DrsXrArbiter/DrsXrSelection.h`) records the runtime and plugin in use and how the plugin came to be (arbitrated, forced or loaded as normal), and `IsValid()` checks the last two against the hardware the vendor table expects and the vendor the runtime implies. That check is the only link between the runtime and the plugin (runtime selection ignores the plugin override). `SetupHmd()` calls `FXrSelection::Get().Validate()` once the HMD, and so the device name, is known; `Validate()` logs a warning when the check fails.
- **Shared early state:** `Drs::XrArbiter` also holds the selected runtime's name and vendor, the runtime table's parsing and the selection rule (`ChooseRuntime`), and `IsNonVrMode()`. These are public so that `DrsXrPlatform` and the tests can reach them; `SetXrRuntime` is private to the module.
- It may use `DrsBase` (e.g. `DRS_LOG`; see `Base/CLAUDE.md` for why that is safe this early). It may use UObject types (the settings, and the USTRUCTs as plain data), but must not touch `GEngine` or subsystems before `PostConfigInit`.

## Desktop OpenXR runtime selection

The arbiter's `StartupModule` selects the OpenXR runtime **before OpenXR creates its instance**, by setting `XR_RUNTIME_JSON`, and records it for `GetXrRuntimeType()`. It runs on Windows only, and not on dedicated servers (the rule a `ClientOnly` module would get). No effect on Android.

- **The runtimes are config:** each `Runtimes` entry has a `Name`, the `Vendor` it implies (none for SteamVR), a list of `Manifest` locators tried in order, and the `RunningProcesses` that mean it is running. `RuntimePriority` lists them, one per line, so a project can reorder or remove them in its own `DefaultDrsXrPlatform.ini`.
- **Selection:** a running runtime wins, otherwise the first installed one in priority order. With none installed, the system's active runtime is used. Under `-noHMD` no runtime is selected. The plugin override is not consulted.
- **SteamVR comes first.** Meta's Link software runs from boot, so Oculus always counts as running; with Oculus first, SteamVR could never be chosen. With SteamVR first, launching SteamVR before the app chooses it. SteamVR counts as running only while `vrmonitor.exe` (its status window) is, since `vrserver.exe` can outlive it.
- **Manifest locators** (`EDrsXrManifestLocator`): an environment variable (`OculusBase`), a URI handler (`steamvr:`, which can be missing), Steam's library folders (from `steamapps/libraryfolders.vdf`), Program Files (Pico), and the OpenXR loader's registered runtimes.
- **The code is in `Private/DrsXrRuntimeSelection.*`** under `Drs::XrRuntime`, with the Windows parts (the locators and process checks) inside `PLATFORM_WINDOWS`. It runs before the engine is up, so it uses no UObjects (the runtime USTRUCTs are used as plain data) and reads options from the command line. It logs with its own category, `LogDrsXrRuntime`, which `Tools/CheckXrRuntime.ps1` looks for.
- **Checking it on a real machine:** the `Drs.XrPlatform.Arbiter.*` tests cover the selection rule with fake inputs; `Tools/CheckXrRuntime.ps1` covers the real locators and process checks. After changing the runtime table, the locators or the selection, run it three ways: with SteamVR open (`-Expect SteamVR`), with SteamVR fully closed so `vrmonitor.exe` has exited (`-Expect Oculus`, with Meta's Link software installed), and with `-Expect None -ExtraArgs '-noHMD'`. No headset is needed, since the runtime is selected before OpenXR starts; without one, OpenXR then fails to start, which is expected.

## DrsXrPlatform: device state and API

- **Higher layers call `UDrsXrPlatformLibrary`** instead of the engine's XR APIs, so vendor and runtime details stay in this plugin. It is a static library: there is no XR subsystem.
- **The state lives in the module** (`FDrsXrPlatformModule::GetDeviceExtensions()`), not a subsystem, because `FXrDeviceExtensions` must register as an OpenXR extension plugin at `PostConfigInit`, before engine subsystems exist. That is also why the module loads at `PostConfigInit`. There is no device state on servers or in commandlets; the library returns defaults there.
- `FXrDeviceExtensions` tracks the worn state (`XR_EXT_user_presence`, else the session state), the system menu (several frames in `VISIBLE`), focus, display refresh rate (`XR_FB_display_refresh_rate`), and GPU utilisation (`XR_META_performance_metrics`, queried on demand; only standalone Quest reports it). `FXrDelegates` broadcasts the changes.
- `FXrControllerExtensions` (`Private/DrsXrControllerExtensions.h`, a second OpenXR extension plugin, owned by `FXrDeviceExtensions` and reached through `GetControllerExtensions()`) tracks the hands and controllers: each hand's controller mode, hand-tracking availability, mixed controller modes and the aim pose of tracked hands. It implements `IXrControllerSource` for the monitor, and broadcasts controller type changes.
- `FXrControllerMonitor` decides each hand's mode from its interaction profile, falling back to joint tracking. It is public and takes an `IXrControllerSource`, so the tests drive it without a headset.
- **Hand tracking** is switched by the Hand Tracking category of `UDrsXrPlatformSettings` (Project Settings > DRS > XR Platform): controllers only, both, or hands only. It replaces MetaXR's Hand Tracking Support setting.
  - The settings class has `Config = Engine`, not the plugin's own file, because the Android UPL reads it and UPL can only read the fixed hierarchies (Engine, Game, ...).
  - `FXrControllerExtensions` uses the hand extensions the engine doesn't, each only where the runtime enables it:
    - `XR_EXT_hand_interaction`: one suggested binding for `/interaction_profiles/ext/hand_interaction_ext`, because the runtime only reports profiles the app suggested bindings for, and `FXrControllerMonitor` needs that profile to see tracked hands.
    - `XR_FB_hand_tracking_aim`: the runtime's aim pose for tracked hands, through hand trackers of its own, since the engine's can't carry the aim state. Without it (SteamVR), `GetAimPose` falls back to the OpenXR aim pose. A data-driven aim pose config is planned.
    - `XR_META_simultaneous_hands_and_controllers`: its structs are declared under Drs names in `DrsXrControllerExtensions.cpp`, because the engine's header lacks them.
- **Android manifest:** `DrsXrPlatform_UPL.xml` holds DRS's manifest entries for every vendor, each inside a condition for the platform it applies to; add new entries there rather than in another UPL. For Meta Quest it sets the hand-tracking permission, feature (required for hands only) and frequency from the settings, removes any hand-tracking version meta-data so the system default applies, and adds `com.oculus.enable_frame_sync`, when Package for Meta Quest is on. The engine already adds the hand-tracking entries and `com.oculus.supportedDevices`; UPL adds skip existing names, so the file removes its entries before adding them. The MetaXR fork doesn't set any of these.
- `SetFloorTrackingOrigin()` asks for OpenXR `LOCAL_FLOOR`, which the runtime may replace with `LOCAL`.
- Config: `Config/Input.ini` sets the OpenXRHandTracking source names that `GetMotionControllerSource` relies on.

## DrsXrMixedReality: passthrough

`UDrsXrPassthroughSubsystem` (game instance) turns passthrough on and off through requests and suspensions; `FXrPassthroughBackend` switches the OpenXR environment blend mode. Passthrough is compiled in only on Android (`DRS_PASSTHROUGH_SUPPORTED`) and needs `xr.OpenXRInvertAlpha` and `r.Mobile.PropagateAlpha`. It is suspended while the `UDrsViewFadeLibrary` fade is opaque, and blending uses the fade's holdout.

## Tests

`DrsXrPlatformTests` holds `Drs.XrPlatform.ControllerMonitor` (an Automation Spec), `Drs.XrPlatform.Arbiter.*` (config text parsing, the vendor and runtime tables, keyword matching, runtime selection, the Project Settings export round trip, and `Arbiter.Selection` for `FXrSelection::IsValid`).
